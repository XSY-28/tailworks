# Notes for coding agents

Several agents work in this repo at once, each on its own branch or
worktree. Most merge pain has come from everyone editing the same few lines,
not from real logic clashes. These rules keep parallel branches out of each
other's way. They come from replaying the last 11 conflicted merges
(2026-11-14).

## Parallel branches: avoiding merge conflicts

### 1. Status goes in `status/<branch>.md`, never in `STATUS.md`

`STATUS.md` is frozen. Write your workstream's results, findings and gaps in
`status/<your-branch>.md`, and touch no other file in `status/`. Details are in
`status/README.md`. (`STATUS.md` conflicted in 10 of 11 merges because every
branch added a `Last update:` line at the top and a section at the end.)

### 2. Only edit `api/openapi.yaml`; regenerate everything else

`mgmt/api/v1/api.gen.go`, `hostd/mgmtapi/v1/client.gen.go` and
`docs/contracts/mgmt-api.md` are generated by `make api`. On a merge
conflict in any of them:

1. Resolve `api/openapi.yaml` by hand. It's the only real conflict.
2. Run `make api`. It rewrites all three files whole, conflict markers and all.
3. `git add` them. `make lint` (api-check) fails if they are stale.

Never hand-merge the generated files. The spec is embedded as plain YAML by
`api/spec.go`, not as oapi-codegen's base64 blob, so a spec change no longer
rewrites hundreds of lines of `api.gen.go`.

### 3. One item per line, and don't always append at the end

Two branches that each add an item to the same single-line list always
conflict. Two branches that each add their own line usually don't.

- **Makefile:** each target has its own `.PHONY: <target>` line right above
  it. Don't bring back the shared `.PHONY:` line.
- **Enums and lists in the spec** (for example `AuditKind`): one value per line
  in both the `description` and the `enum`.
- **Go composite literals, struct fields, `switch` cases, flag lists:** use
  one per line, as in `hostd.New`'s `&Host{...}`. When you add a field to a
  gofmt-aligned struct, give it its own comment-separated group, so a longer
  name doesn't realign (and conflict with) its neighbours.
- **Where order doesn't matter, insert in sorted or logical position**, not at
  the end of the list. The end is where every other branch is appending too.

### 4. Put new feature code in new files

The hotspots that conflicted most were `hostd/host.go`, `hostd/http.go`,
`hostd/workload.go`, `hostd/objects.go`, `netd/registry.go`,
`mgmt/service.go`, `mgmt/sqlstore.go`, `cmd/twd/main.go` and
`cmd/twd-hostd/main.go`. Put the feature's logic in its own file
(`hostd/public.go`, `mgmt/placement.go` and `mgmt/warmkeys.go` are good
examples). Keep the edit to the shared file small: one field, one route
registration, one call. Don't reformat or reorder code you aren't changing.

### 5. Don't claim an ADR number on a branch

Branches that drafted ADRs in parallel picked the same "next" number:
smart-placement drafted ADR-030, which fast-vm had already taken, and had to
renumber to ADR-033 across the code, docs and Makefile. While a decision is
Proposed on a branch, call it `ADR-<slug>` (for example
`ADR-smart-placement`). Give it the next free number only when merging to
master, and replace the slug everywhere in that same change
(`git grep ADR-<slug>`). If ADRs live in this repo, use one file per ADR,
not one shared `DECISIONS.md`.

### 6. Stay close to master

- Merge `origin/master` into your branch early and often: when you start,
  after any PR lands that touches your hotspots, and right before you open
  the PR. Ten small conflicts are easier than one big one.
- When two workstreams need the same refactor (a new store method, a shared
  type, a schema column), land it first as its own small PR, then build on it.
- After resolving conflicts, run `make lint test` before you push. A clean
  textual merge can still be semantically wrong; the 11-file fast-identity ×
  public-ingress merge was one.
- Never use bare `git stash` / `git stash pop`. The stash stack is shared with
  every other worktree. Use a WIP commit instead.
